# Bounded browser repair loop

The local Docker workspace supports **Investigate and repair** after file preview, provider-submission consent and separate loop approval. One investigation is followed by a focused proposal and real isolated baseline/candidate tests. A failed candidate can trigger one additional proposal using bounded failed-test evidence. A blocked runner, provider error or quota stops the loop. Every proposal is hash-bound to the original selected source; existing test files are read-only. No host repository changes are applied.

The loop reserves three model calls and two verification attempts from the app's shared minute budgets. These are maximum reservations, not a claim all calls occurred. The worker retains its own verification limit. The browser disables inputs during execution, records attempts and shows the final diff and complete replacement. Downloading a candidate still requires final patch-review approval. A passing test report has only the selected Python standard-library unittest scope; it does not verify every finding or certify security.

The live synthetic checkout loop passed on 2026-10-14 with NVIDIA trial inference and Docker: one investigation, one proposal and one verification attempt; original five tests had two errors and candidate five passed. No original project changes were applied. Tests separately cover a second proposal after failure, the attempt cap, provider errors, missing/blocked execution, invalid candidates and explicit approval/rate boundaries.

NVIDIA remains for internal trials only. A hosted deployment needs an appropriate provider and verified free account; no fallback, billing upgrade or credit purchase occurs automatically.
