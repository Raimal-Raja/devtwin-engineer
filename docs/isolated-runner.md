# Local isolated verification

The local workspace has an execution integration for comparing original selected files with an approved candidate. Docker Desktop is installed and live original/candidate execution has passed on the synthetic checkout fixture, including the Dockerized app-to-worker route. Missing tooling/image, time/output limits, invalid reports and uncertain cleanup produce a blocked status, never a claimed test pass.

For local development, follow [Docker setup](docker.md). Docker Desktop uses Linux containers through WSL on this Windows computer. Review the official [licensing](https://docs.docker.com/subscription-billing/desktop-license/) terms for your use. Installation did not automatically accept the agreement; the user confirmed the engine was running after first-start setup.

An eventual Linux server would run the same backend and local Docker Engine on a dedicated machine, with production authentication and job controls. Docker software does not supply that machine or make public hosting free. Local execution avoids renting a server for development; public hosted execution needs a separately verified hosting/resource plan.

The operator must preload an official Docker Hub Python image and set `DEVTWIN_RUNNER_IMAGE` to its exact `python@sha256:…` reference. No image tag/default digest is invented and the runner does not pull images automatically. Select a reviewed Linux image for the desired architecture, confirm its repository digest after pulling and configure that actual value. Registry downloads occur during setup, not during project checks.

Review the proposed patch in the local page, approve it and separately approve isolated execution. Click **Run isolated checks**. The backend runs standard-library `unittest` discovery on the original selection, then the candidate, preserving selected test bytes. Each process has a 30-second limit plus bounded cleanup grace. Output is capped; no/all-skipped tests do not count as success. Candidate failure remains a failure. An observed baseline failure followed by candidate passing is recorded separately from an already-passing baseline.

Source files enter the container through bounded JSON stdin and are written only to its temporary filesystem. No host source mounts, Docker socket mounts, provider/GitHub/session environment credentials, shell commands or dependency installation are supplied. Container options include network disabled, read-only root, unprivileged user, dropped capabilities, no-new-privileges, process/memory/CPU limits, bounded tmpfs and disabled daemon logging. The CLI uses an empty temporary Docker configuration and a fixed local daemon endpoint. It requests cleanup only for the generated container name owned by that job.

These controls have simulated command/protocol tests, missing-runtime checks and a live container repair check. They are not yet a validated production sandbox or multi-tenant security audit. Project code can manipulate its own tests/reporting; passing results do not prove correctness. Small selected-file Python unittest suites are supported in design. FastAPI or other dependencies need a separately reviewed runner image/strategy; packages are not installed during execution. The browser's production repair loop and hosted job service remain unfinished.
